A arquitetura oficial define exatamente os quatro componentes que manipulam telemetria — receivers, processors, exporters e connectors — enquanto extensions adicionam capacidades ao Collector que não ficam diretamente no fluxo da telemetria.

1. Primeiro: o que entra no Collector?

Antes de pensar em receiver, pense em sinais.

O Collector trabalha principalmente com:

                    OpenTelemetry
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
       TRACES         METRICS          LOGS
          │              │              │
          │              │              │
       Spans          Metrics         Records

E existe uma quarta área que está ganhando importância:

                    PROFILES

O ecossistema já possui componentes relacionados a profiles, mas traces, metrics e logs continuam sendo os três tipos de pipeline principais na configuração tradicional do Collector.

2. RECEIVERS — de onde o dado entra

O receiver é a porta de entrada.

Ele pode:

receber dados;
escutar uma porta;
fazer scrape;
consumir arquivos;
consultar APIs;
consumir filas;
coletar dados do host;
coletar dados do Kubernetes;
receber dados de outros sistemas.

A documentação oficial define receivers justamente como componentes responsáveis por coletar telemetria de diferentes fontes e formatos.

11. TRANSFORM — uma das áreas mais importantes

Aqui chegamos exatamente ao seu exemplo.

O:

permite modificar a telemetria usando OTTL — OpenTelemetry Transformation Language.

Visualmente:

Receiver
   │
   ▼

   │

   ├── delete

15. Tail Sampling

Muito mais interessante.

O Collector espera informações suficientes da trace antes de decidir.

              TRACE
                │
       ┌────────┼────────┐
       │        │        │
     Span     Span      Span
       │        │        │
       └────────┼────────┘
                ▼
          TAIL SAMPLING
                │
        ┌───────┴────────┐
        ▼                ▼
      KEEP              DROP

Por exemplo:

if:
  status == ERROR
  → KEEP

if:
  latency > 2s
  → KEEP

if:
  service == payment
  → KEEP

else
  → DROP

É uma ferramenta extremamente poderosa para reduzir custo sem simplesmente jogar fora traces importantes.

O ecossistema atual é muito maior que o otelcol core. O Explorer oficial atualmente mostra uma grande quantidade de componentes de receivers e demais componentes, distribuídos entre core, contrib, Kubernetes e outras distribuições.

Por isso, "mapa completo" pode significar duas coisas diferentes:

Mapa arquitetural completo — que é o que montei acima: todas as camadas, relações e possibilidades.
Catálogo de componentes — literalmente cada receiver, processor, connector, exporter e extension existente no v0.159.0, com nome, finalidade, sinal suportado, estabilidade, distribuição e exemplo de uso.

Para o que você está querendo estudar, o segundo formato é provavelmente o próximo passo ideal: uma espécie de "OpenTelemetry Collector Knowledge Map", organizado em árvore, onde eu colocaria todos os processors atuais (incluindo Transform/OTTL), todos os connectors, receivers, exporters e extensions, e ainda marcaria Core / Contrib / K8s / Alpha / Beta / Stable / Deprecated. A documentação oficial mantém justamente essas informações por componente.

Se você quiser usar isso como material de estudo/documentação interna, eu também consigo transformar esse mapa em um diagrama visual gigante do OpenTelemetry Collector, mostrando os caminhos OTLP → Receiver → Processors → Connectors → Pipelines → Exporters → Grafana/Prometheus/Loki/Tempo, incluindo as possibilidades de branching e mudança de sinal.
